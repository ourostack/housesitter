# Security

housesitter types a password into a computer with nobody watching. This is how it keeps that safe, and where its protection ends.

## What it protects

- **The Mac's password** is copied once, from your Keychain, over SSH stdin, to the KVM. There the sitter seals it with a key derived from the KVM's own hardware ids (its eMMC CID and SoC serial) and stores it root-only (0600). It is never in a process's argv, a log, `status.json`, a gist, a notification or a cloud.
- **Disarmed by default.** A stored password is *unverified* and is never typed. One supervised trial (`housesitter unlock <mac> --trial`) can move it to *verified*, and only if that try ends at the desktop; a new password resets it. A desktop appearing on its own never counts.
- **It is typed only at a taught prompt on the KVM's own picture.** Where kvmd's OCR is unavailable, new lock lessons require separate operator-marked regions for the empty password field and hint. Both signed-contrast templates must match at least 90% at one common, bounded translation; the hint cannot stand in for the field, even when it is inside it. Wallpaper outside those regions is not part of the match. The [teaching and migration instructions](usage.md#lock-lessons) state the layout limits. Legacy lessons remain readable and are not silently made more permissive: they keep their original steady-bright-pixel matcher, which can include wallpaper or avatar pixels. Once a widget-based lock lesson exists, legacy lock matches cannot bypass it. FileVault lessons and user-list click lessons are unchanged. Agents' ordinary clicks, keys and typing still need a fresh desktop read. A desktop, a dark screen, an unknown screen or a prompt on another display is a refusal for password entry. Lock-screen policy, password verification, boot checks and budgets remain separate gates; a boot alone never authorises typing.
- **Budgets.** At most three unlocks an hour across incidents; two failed unlocks in one incident and it stops and tells you.
- **No command carries a secret.** No command carries the password. `housesitter unlock` asks the sitter to type its own copy, under the same checks. `type` refuses text that looks like a password or token, because on the outbox route it passes through a gist.
- **Named secrets, typed by the sitter when an agent asks (`type_secret`).** Besides the Mac's password, the sitter holds any named secret (`setup-password`, `apple-account`, …), sent once from a Mac's Keychain over SSH stdin (`housesitter secret <mac> <name> --kvm`) and sealed like the password. An agent that sees a password prompt on the Mac asks the sitter to type one by name, saying which prompt it sees; the agent never holds the value. The design trusts the agent to judge the prompt, and these gates hold it to the picture it judged:
  - *Who can ask:* root over SSH (`sitter.py do type_secret`) and Housesitter's own MCP tool (`sitter_type_secret`), which runs on the KVM. Never the GitHub outbox: its token can also take screenshots, so a secret typed through it into a visible field, or a prompt that echoes it, could leak through the same gist. The Mac's watch key (`watch-only`) can't ask either.
  - *Only at the picture the agent judged:* the KVM can't read the Mac's keyboard focus, so the agent judges it from a screenshot or look (a caret in the field, a highlighted field, the prompt's words) and passes that picture's frame id (`seen`): 16x9 grey cells at 4 bits, the time it was taken, and a tag made with this KVM's device key, so only the sitter mints one and it keeps nothing to check it. Just before typing, the sitter takes a fresh picture (three tries, a second apart, if taking it fails; then it refuses and says so) and refuses unless it matches `seen` within a small tolerance (picture noise and a blinking caret pass; a sheet that closed, a window or notification that came up, does not), `seen` is under 30 seconds old, and the KVM can see the screen: each frame id records whether kvmd (or, where its streamer says nothing, the KVM's HDMI receiver) reported live video before and after the picture, and both `seen` and the check picture must be live and not near-uniform (cells' spread under 6 grey levels), since kvmd's "NO LIVE VIDEO" placeholder and a stale decoded frame are pictures too. Otherwise it refuses: "the KVM can't see the screen". What it can't tell: the frame's cells are too coarse to see a caret move between two fields of the same dialog, and `classify_frame` can't tell a desktop with a sheet or a `sudo` prompt in Terminal from a plain desktop, so a desktop isn't refused on its own; that judgement is the agent's.
  - *What:* only a secret the sitter holds; never the KVM's own credentials (`kvmd`, `outbox`, `plug`, `ntfy`), which it uses itself. The Mac's own password is refused while the sitter's last look, or a boot under way, says the Mac is at a FileVault, login or lock screen: there it is `unlock`'s, with the password gate, the taught prompt and three an hour.
  - *How often:* 20 typed secrets in any hour, all names together, each recorded as started on the KVM's disk before it is typed, so a crash or reboot buys nothing.
  - *Audit:* one line in the sitter's log, and one ledger entry, per use: the secret's name, the prompt the agent described, who asked (SSH or the MCP tool) and the time. Never the value, nor its length. The ledger's newest entries go into `status.json` (and the outbox gist, when there is one) with the name only.
  - *Where it ends:* whoever can ask can have any held secret typed into whatever has focus on the Mac, including a text field that shows it. An agent that is wrong about the prompt can type a password into a chat box or a document. Hold on the KVM only the secrets a setup needs; `housesitter forget <mac>` wipes every one of them, with the rest of the sitter's secrets.
- **Messages say what, never the secret.** A message carries the Mac's name, its state and what to fix. An ntfy topic made by `--notify ntfy` is private only by its random name (like a secret gist), so anyone who learns it can read those messages; use a webhook you control, or your own ntfy server, if that matters.
- **A heartbeat URL can be a secret.** A `json_age` probe's URL (a secret gist, say) stays in the KVM's root-only config; the sitter never logs it, and `doctor` and `status` show only the heartbeat's age.
- **Email goes through your ntfy.sh account.** With `--email`, the sitter holds your ntfy access token, sealed like the Mac's password. Anyone with that token can post to your topics and send up to your account's daily emails to your verified address; revoke it at ntfy.sh under Account. The address is in the KVM's config, and ntfy.sh sees every message it forwards. From 0.2.2 the sitter's log and ledger say only "emailed"; 0.2.1 wrote the address there too, and `doctor --private` shortens any address to its first letter.
- **The Mac's watch holds a copy of the ntfy token.** `housesitter watch-kvm` sends its messages from the Mac, so with `--email` it reads your ntfy token from the Mac's Keychain at send time; it never writes it to its state file or log. Give it a key of its own, forced to `sitter.py watch-only` in the KVM's authorized_keys (see the README): that key may ask `watch_check` or `status` and nothing else, and the command is split without a shell. The sitter accepts `watch_check` only over SSH, never through the GitHub outbox. It can record who watches and add the Mac's own sends to the ledger; it can't type, click or unlock.
- **The KVM is pinned, and the first contact is honest about trust.** The client pins the KVM's TLS certificate at `adopt` and refuses a different one afterwards. The first contact is trust on first use: whoever answers at that address first is pinned. To verify it out of band, read the fingerprint on the KVM itself, on a console you reach without the network (`python3 /etc/kvmd/user/housesitter/sitter.py fingerprint` once the sitter is there, or `openssl x509 -noout -fingerprint -sha256 -in` its certificate), and pass it to `adopt --fingerprint`. `adopt` also asks the KVM, over SSH, for its own certificate's fingerprint and stops if that differs from the one pinned over HTTPS. That is a cross-check between two channels, not proof, since both were first trusted the same day. Without either, adopt on a network you trust: your home LAN, cable to cable. The GL.iNet Comet has no display of its own to show a fingerprint on.
- **Write-ahead.** Every unlock and power action is recorded as *started* on the KVM's disk before it happens, and every limit counts those entries, so a crash or reboot mid-action can't buy an extra try.
- **A guarded power cycle.** Before cutting power, the sitter looks again, three times across more than two minutes: only a desktop whose clock never moves, while its network probes fail, is cut. A boot, FileVault, a login window, a black, unknown or update screen never is. `--attended` is the explicit override for a person who has looked.
- **No reshaping.** EDID writes, factory resets and firmware upgrades are refused below every kvmd call, in Node (`refuseReshape`, in `httpsRequest` and every client call) and on the KVM (`refuse_reshape`, in `Kvmd.request`).
- **The KVM reaches nothing, and away from home little reaches it.** On your tailnet it is `tag:kvm` with no outbound grants (`housesitter tailnet-policy`). GL.iNet's cloud binding is turned off and must read back as disabled, or `harden`, and so `adopt`, fails. Ingress follows where the KVM lives. At `location: home` the `HOUSESITTER_IN` chain lets `lo`, `tailscale0` and private sources (10/8, 172.16/12, 192.168/16; link-local and ULA for IPv6) through, then drops SSH (22), HTTP (80, which only redirects) and HTTPS (443). Home trusts every private address, so it is for a network you control; an office or café network is private too. Anywhere else (`away`) SSH, HTTP and HTTPS answer only on `lo` and `tailscale0`. Both are read back from the kernel (each allow and DROP present, every allow before every DROP, no rule we didn't write, INPUT jumping to the chain), or `harden` refuses; the sitter reads them back every 5 minutes and puts them back if they changed. Where `ip6tables` is missing (the Comet has none), `harden` turns IPv6 off on every interface but `lo` and `tailscale0` and reads that back, or refuses, at home too. It refuses away mode until `tailscale0` is up, so it can't lock you out. The Comet's kernel has no connection tracking, so a session open from a place the new mode doesn't allow ends when the mode changes. UDP (the KVM's NTP and mDNS) isn't filtered. Both modes ran on our Comet on 9 November ([the proof](proof/2026-11-09-ingress/)).
- **The outbox token** is gist-only, sealed on the KVM like the password. Requests carry an id, are marked seen before they run (never twice), and are dropped after 10 minutes.

- **Setup mode widens the agent's hands, for hours, by root only.** `sitter.py setup-mode on --mac <label>` (root on the KVM, or Housesitter's own MCP tool; no outbox op sets it) lets an agent click, press keys, type and `type_secret` on any screen, Escape excepted, over SSH or MCP; the outbox keeps the normal desktop-only rules. While it's on, the sitter types nothing by itself and refuses unlock and power, so the usual Mac's password and lessons never meet the other Mac. It expires by itself after at most 24 hours.
- **The agent can message the owner directly (`notify`).** Housesitter's `sitter_notify` (or `sitter.py do notify` over SSH; never the outbox) posts one line, and optionally a small screenshot, to the sitter's own notify target (ntfy and its email, or a webhook), 12 an hour, sharing the daily email cap. The sitter refuses text that holds any secret it keeps. A screenshot goes to the notify target (on ntfy.sh, a public server: the topic's name is its only lock), so the skill attaches one only for a QR code or a number to match.
- **Sealing needs root on the KVM.** `sitter.py store-secret` runs only as root on the KVM, so in practice a controller Mac (`adopt`, or `housesitter secret <mac> <name> --kvm`, over its root SSH key) or Housesitter itself seals a secret. No op seals one: nothing that arrives through the GitHub outbox or the peer link becomes a secret on the KVM.
- **Two homes for the KVM's keys.** The KVM's admin password and a root SSH key should each live on at least two Macs. `housesitter doctor <mac>` says whether this Mac holds both and warns when the config's `controllers` lists fewer than two: on 19 November both lived only on a laptop, and wiping it locked everyone out of the KVM.

## Where it ends

- **Root on the KVM can read the password.** The seal makes a copied file useless elsewhere (a backup, a support bundle, a pulled card); it does not stop someone who controls the running KVM. Treat the KVM like the Mac's keyboard with the password taped to it: physically and on the network, keep it as private as the Mac.
- **Pixel recognition is not authentication of macOS.** Teaching requires an operator who has verified the real lock screen and empty field on the KVM. A malicious full-screen imitation can reproduce pixels; neither the old matcher nor the widget matcher proves the operating system's identity. No OCR model or general “looks like a login” fallback is allowed to widen this gate.
- **Anyone with the KVM's admin password can drive the Mac's keyboard and see its screen.** That's what a KVM is. Keep it off shared networks and behind your tailnet.
- **`"unlock_lock_screen"` trades your screen lock for agents' reach.** Off by default. With `"on_request"`, anyone who can ask the sitter (SSH to the KVM, the GitHub outbox, or an agent you let drive it) can have it unlock your lock screen within the budgets; with `true`, any lock screen it sees is unlocked. The password still never leaves the KVM, and every gate still holds (a verified password, a lesson on its own picture, three an hour). Turn it on only for a Mac that exists to run agents, and only if no policy you're under requires the screen lock.
- **The smart plug has its own password,** made by `housesitter plug <mac> adopt`, kept in your Keychain and sealed on the KVM. Shelly's cloud is turned off and read back as off. Anyone on the plug's network who learns that password can cut the Mac's power.
- **The sealing is standard-library crypto** (HMAC-SHA256 in counter mode, encrypt-then-MAC) because a KVM's Python may have no AES module and nothing should need installing on it.
- **Microphones:** the GL-RM1PE has none that we know of. Some KVMs have shipped with one undocumented ([NanoKVM](https://github.com/sipeed/NanoKVM/issues/693)); check yours.
- **Managed Macs:** if your Mac is managed by an organization, check its policy before you put a KVM on it and its password on the KVM.

Found a problem? Open a [security advisory](https://github.com/ourostack/housesitter/security/advisories/new).
